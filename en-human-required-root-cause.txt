10. Proven Root Cause and Recommended Correction
------------------------------------------------
- Root Cause (Electron Runtime Defect):
  In src/main/auth/auth-script-runner.ts, AuthScriptRunner.run() calls detectHumanRequired(webContents) after every completed step (line 384).
  detectHumanRequired() ran `document.querySelector('#wp-auth-check')` without checking visibility.
  WordPress wp-admin pages (including /wp-admin/post-new.php) ALWAYS render `<div id="wp-auth-check-wrap" class="hidden"><div id="wp-auth-check">...</div></div>` in the footer even when the user is logged in and no interim login modal is visible.
  Earlier failed runs (VI Release 4) failed on Step 0 before AUTH_STEP_COMPLETED, so detectHumanRequired() never ran. As soon as EN Step 1 succeeded, detectHumanRequired() ran for the first time, matched the hidden `#wp-auth-check` element, and immediately aborted the job with `HUMAN_REQUIRED (captcha_or_verification_ui)` before Step 2 could start.
- Correction Implemented:
  1. Updated `detectHumanRequired` / `HUMAN_REQUIRED_DETECTION_SCRIPT` in src/main/auth/auth-script-runner.ts so `#wp-auth-check` only triggers `captcha_or_verification_ui` when it (and `#wp-auth-check-wrap`) is actually visible (not `.hidden`, not `[hidden]`, not `display: none` / `visibility: hidden`, and non-zero bounding rect), while keeping all CAPTCHA selectors and text checks intact.
  2. Updated `CAMPAIGN_JOB_FALLBACK_DECISION` in src/main/jobs/campaign-job-executor.ts so `mutated` is `true` when `stepsExecuted > 0` for non-`"error"` outcomes (such as `human_required`).
  3. Added regression tests in tests/auth-human-required-wp-auth-check.test.ts.
